# Performance and responsiveness tracker

This is the implementation backlog and evidence record for multiplayer performance. It covers the transport, room relay, table replica, shared shop, spectator view, and native UI bridges present in this repository. Stable `PERF-*` and `GAP-*` IDs are intended for follow-up changes and regression reports.

**Current evidence: static audit plus native macOS correctness fixtures.** The bounded screenshot harness exercises native rendering and the scenarios recorded below. No before/after frame-time distributions, network RTTs, payload-size distributions, GPU timings, or live cross-platform sessions were measured. “Implemented; unmeasured” means code and functional checks support the mitigation; it does not mean the lag report is resolved. Selected inherited game methods were also inspected through static decoding of the Ultrapool 0.15.7 resource pack. Native costs, driver behavior, and real Steam routing still need profiling.

The [Slay the Spire 2 comparison](#slay-the-spire-2-comparison) adds reference designs from its installed v0.107.1 assembly/documentation and its multiplayer developer's published explanations. It is a static architectural comparison, not a benchmark between the games.

## How to maintain this tracker

| Field | Meaning |
| --- | --- |
| Priority | `P1`: first candidates for visible stalls or input delay; `P2`: throughput, repeated work, or transition costs; `P3`: smaller/conditional costs. Priority is a static assessment, not a measured ranking. |
| Evidence | `V`: verified in repository code; `N`: additionally verified from native 0.15.7 script tokens; `H`: plausible cost still to inspect or profile. None is a runtime timing measurement. |
| Status | `Open`; `In progress`; `Partial; unmeasured`; `Implemented; unmeasured`; `Retired: feature removed`; `Verified` only after the acceptance check passes and the evidence is linked. A mitigation can leave a residual task open. |
| Acceptance | A concrete behavior or measurement required to close the item. Runtime acceptance requires the explicit authorization and harness in [AGENTS.md](../AGENTS.md) and [screenshots.md](screenshots.md). |
| Updating a row | Preserve its ID. Record the final fix, the check actually performed, and the remaining limitation. Add a dated evidence row below; do not convert estimates into measurements. |

The default screenshot harness caps rendering at 30 FPS. It can validate correctness and report frame costs at that cap, but it cannot establish a 60 FPS result. Any different performance configuration must be an explicit, bounded extension of that harness. Do not create an additional game launcher to collect timings.

## Critical paths and cadence

| Path | Call chain / baseline work | User-visible consequence |
| --- | --- | --- |
| Client receive frame | [`transport._process`](../mod/transport.gd) → `_receive_wire` → synchronous `received.emit` → [`main._received`](../mod/main.gd) / `_received_table` → validation → native replica/shop updates. | Packet decoding, reconciliation, native resource creation, and UI work all occur on the same frame path. Receiving more samples can delay drawing even when network latency is low. |
| Table update | `main._process` → `_publish_snapshot` → [`table_sync.capture`](../mod/table_sync.gd) → room relay → `table_sync.apply_snapshot` → [`replica_game.apply_table`](../mod/replica_game.gd). | Baseline snapshots run every 0.10 s and include inventory, results, pockets, full item descriptors, and motion. Baseline shop snapshots use the same cadence. |
| Shop command | [`shop_sync._submit`](../mod/shop_sync.gd) → `_table_send` → room host → table leader `handle_request` → native action / save → result → client `apply_result`. | A predicted visual response can be immediate, while the next mutation still waits for host confirmation. Host frame stalls and relay latency both lengthen that wait. |
| Remote-led table | Guest → room host → table leader; reply returns table leader → room host → guest. If the room host leads the table, only the direct request/reply pair is needed. | Remote-led tables add two one-way relay legs and two relay-frame scheduling opportunities. No fixed millisecond penalty can be inferred without measurement. |
| Periodic state | `main._publish_state` every 0.15 s, plus event/targeted sends; `presence.tick` every 0.05 s. | Approximately 6.7 state updates/s/table and 20 cursor updates/s/active player at steady frame cadence, before event-triggered sends. These are configured rates, not measured throughput. |
| Spectator | Relay cache → `table_spectator.apply_snapshot` → 0.12 s interpolation buffer → `tick` every rendered frame. | The spectator intentionally trades 120 ms of presentation delay for interpolation; this is separate from the player's own input latency. |

## Slay the Spire 2 comparison

The strongest transferable lesson is to separate local presentation from synchronized transactions. STS2 also added multiplayer to an existing single-player game, but its developers could build on largely separate gameplay models and visual nodes. Its developer describes a substantial period of multiplayer testing and refinement, rather than a transport setting that made it smooth. [Development account, April 19, 2026](https://straypixels.net/sts2-multiplayer-timeline/)

Our shop combines a shared economy, one outstanding client command, native UI reconciliation, and synchronous host-side persistence. That creates several independent ways to feel slow. Pool physics adds a separate synchronization problem during shots; it is not a sufficient explanation for shop lag, where replica bodies are frozen. The comparison below identifies mechanisms and useful designs, not measured causes of any particular play session.

### Evidence scope

STS2's developer describes deterministic action execution without frame lockstep: peers may animate the same ordered actions at different speeds. The same account describes state checksums and divergence diagnosis, with disconnect/reload rather than seamless arbitrary-state recovery. Those designs do not establish cross-platform determinism for native pool physics. [Determinism, May 20, 2026](https://straypixels.net/sts2-multiplayer-determinism/)

Keep our receive budgets, packet validation, queue/cache bounds, transaction authority, and resync facilities. STS2's inspected receive loops, some buffers, and loading completion paths would not satisfy all of this project's frame-budget rules. Neither C# nor an `async` keyword guarantees that a callback avoids blocking the engine. Adopt the useful separation of responsibilities without assuming the reference implementation is universally faster.

The reference also has documented performance and correctness work: the official v0.107.1 notes report first-use combat-effect stutter improvements alongside multiplayer divergence fixes. That corroborates resource preparation as a useful investigation, not a claim of hitch-free rendering. Newer beta behavior is outside this installed-build comparison. [v0.107.1 release notes, June 18/19, 2026](https://steamcommunity.com/games/2868840/announcements/detail/710026912607505281)
