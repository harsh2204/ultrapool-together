# After-hours rack

When a table finishes, its players can browse the final build on a felt board while the other tables keep playing. Table buttons switch between finished builds; unfinished tables show their current status. **Lobby & live tables** opens the existing lobby and spectator controls. **Final racks** reopens the review after leaving it.

The board combines the native saved-run inventory artwork with Together's table controls. It displays the recorded triangle and reserve slots, four snack slots, extra build slots and negative cubes, plus each table's players, final score, shots, round and equipped cues. Ball names use the game's translated resource getters; mixed balls retain both names and the native mixed-ball material. Hover an item to inspect its recorded traits.

Each ball's visible points are its captured `base_score + temp_extra_score`, matching the native item value. This is not the ball's contribution to the run total or a prediction including future pocket multipliers and abilities. Native number formatting is applied to the magnitude, retaining the sign for negative values. Levels use native spark art; snacks retain their native texture, rarity plate and applicable counter, including Gummy Brain's copied snack counter.

After their own table finishes, connected players can drag balls in any available final rack to discuss its build. Dropping onto an occupied slot swaps the two display positions; dropping into an empty slot moves the ball there. Every viewer receives the arrangement and held-ball movement. Only one player can hold a ball per table, and a player cannot hold balls in several tables at once. Escape, dropping outside a slot, leaving the review or switching tables cancels the move. **Reset arrangement**, available when no ball is held, restores the original recorded order for everyone. Snacks and negative cubes remain inspection-only. Discussion changes neither the immutable final build nor native inventory, ball values, match scores or progression.

Once all tables finish, a brief chalk rack appears for the leading table. Tied score results share the chalk. Race results use the room's recorded finish order; a failed co-op run or a race with no successful finisher gets a neutral closing message. A completed table keeps its result if its leader later disconnects. A table whose leader disconnected before finishing cannot win.

**Continue** becomes available when the room is finished and every connected table's final build has arrived. A disconnected table with no saved final build is clearly marked unavailable and does not block leaving. Continue reveals the native result card when there is one, or opens the lobby for a score-limited match. Native Main Menu, Restart and Endless buttons retain Together's existing lobby behavior. This feature does not add multiplayer endless continuation.

## Ownership and delivery

Together **0.12.0 / protocol 12**, using **UP12** room codes, requires all participants to support the final-build record. Native Ultrapool remains **0.17.2**. Older protocol peers cannot join these rooms.

The table leader captures its inventory and equipped cues once after publishing its finished state. The authenticated `final_build` table message always travels reliably. The room host accepts it only from the assigned, connected table leader, for the current match and table, after a terminal summary has been recorded. Cue owners must belong to that table. Accepted records are immutable: identical retransmissions are harmless; conflicting replacements are rejected.

The room host relays accepted `run_build` records reliably to all room members. Clients accept them only from their room host, with matching match/table/leader identities and validated resources. The normal reliable ordering is finished state → room summary → final build. An authenticated table resync also receives the room's archived builds. A final inventory is independent of render-snapshot readiness: an unfinished spawn or rejected visual snapshot cannot consume the inventory archive's delivery.

Each record is bounded to **96 KiB**, with at most **eight records per match**. Existing inventory bounds remain 64 build slots, four passive slots and 64 negative-cube slots; cue inventories remain bounded to eight players. No native resource objects, arbitrary extension data, scenes or filesystem paths enter this record. Disconnecting the source table does not erase an accepted build; ending the match, leaving the room or starting a new match clears the archive.

## Shared discussion ownership

`end_run_discussion.gd` stores a separate display-order permutation over the original inventory slot identities, including empty slots. It keeps at most eight table states with 64 slots each and validates a maximum serialized state size of **4 KiB**. The archive remains the source for ball art, traits and values; rearranging its display never writes to the archive or native inventory.

The room host coordinates reliable `rack_request` **begin / drop / cancel / reset** actions and publishes reliable `rack_state` replies. It requires a connected room member whose own table has finished, a current-match target with an archived build, the current revision, valid slot identities, and the host-issued hold token for release. A competing or stale action returns the current state and a rejection to its sender. Clients accept shared state only from the room host. Revision, token and sequence checks prevent old grabs, releases or movement from crossing later actions. The transport rejects request/state messages sent over the disposable channel.

Held-ball `rack_motion` uses the disposable channel. Local pointer feedback is immediate; the sender and host admit at most one sample per **50 ms (20 Hz)** for the held table. Each accepted sample replaces one bounded position, with no motion queue. Coordinates are finite and normalized, actor/token identity must match the hold, and sequence numbers must advance. The host forwards accepted movement to connected viewers. Reliable drop/cancel/reset remains separate and supersedes late movement. A same-revision resync cannot rewind a newer motion sample.

Authenticated resync sends the final archive before its current discussion state. A disconnect reliably releases that actor's hold without removing the recorded build. Session teardown/rematch clears arrangements, hold tokens and motion timing. A quick mouse release before pickup acknowledgement retains one pending drop or cancel until the token arrives; changing tabs or hiding the review preserves that cancellation intent.

## Native presentation and cost

The native game still completes its own run, saves and unlocks normally. The mod does not replace the game scene, execute guest result gameplay, falsify `in_menu`, or rerun the native ending callback. It covers only the existing result popup's content and underlay CanvasLayers while the review is active. Popup registration, native pause state and processing remain intact. Continue restores the original layers and valid keyboard focus; teardown restores them before the existing service cleanup closes menus.

Review navigation belongs to each player. Incoming and already-queued leader UI navigation are ignored once that player's table has finished, so another player opening the lobby cannot interrupt build inspection.

Under **PERF-008/010/014/019/024/026 and GAP-004**, this adds one reliable final inventory per table, a bounded discussion state and drag-motion traffic while a ball is held. `end_run_native_rack.gd` constructs one retained, scriptless copy of the native saved-run inventory scene. It reads the native triangle/reserve markers and snack slots, hides run-only metadata absent from the archive, and adds bounded rows for extra balls and cubes. Standard racks scale to the viewport; expanded racks use a supplemental scroll region.

Native ball, passive and slot templates, sphere materials, level sparks and rarity plates load during service setup. Exported arrays are copied; local shader instances own their changed parameters. The selected build hydrates retained pools of at most 64 build balls, four snacks and 64 cubes. Materials change only when a ball's normal/mixed representation changes. No native item setup, score callback, passive registration or resource mutation is executed. Unchanged records preserve item nodes and focus. Discussion motion moves only the held art and actor label; changed order repositions the existing nodes. Summary refresh does not rebuild the native rack. One finite chalk tween handles the closing accent and is cancelled on teardown.

Session cleanup hides and resets the rack while retaining its bounded pools for reuse; service teardown frees its native templates and presentation nodes. There is no recurring resource discovery, disk I/O or scene construction during dragging. Setup and first-use pool/material construction remain synchronous costs. The tradeoff is bounded memory and message traffic for immediate local movement and shared discussion. The current native-rack hybrid and discussion controls are **implemented, unmeasured**; static inspection does not establish engine compatibility, rendered fit, input latency or a performance improvement.
